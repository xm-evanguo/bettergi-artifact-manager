# 圣遗物整理与强化规划

> 本文件是从 BetterGI 主程序仓库复制的原始规划快照，保留当时的阶段状态。当前实现见 [实现状态](IMPLEMENTATION.md)。

状态：第 1 版，2026-10-29，规划，尚未实施。  
代码依据：本地 `875a941e`；社区脚本按本次调查时的源码核对。  
关联：[脚本仓库与任务资源](../../better-genshin-impact/Docs/design/pulonia/repository-resources.md) · [JS 脚本自定义 HTML 设置页](../../better-genshin-impact/Docs/design/js-script-html-settings.md)

## 1. 目标与实施顺序

背包中的圣遗物已经爆仓。用户难以判断哪些值得强化、哪些可以清理，首要目标是减少逐件查看和判断的负担，释放可继续获取圣遗物的空间。

先最大化利用已有 JavaScript 脚本，形成“扫描背包 → 按角色需求评估 → 输出清理清单和强化队列 → 用户复查处理”的流程。首版以释放背包空间为交付目标；精确配装、联网更新攻略和自动强化逐步加入。

| 优先级 | 交付结果 | 完成条件 |
| --- | --- | --- |
| P0 | 能说明哪些可以清理、为什么，以及先强化哪些 | 首版报告可定位到游戏中的物品；用户能据此完成一轮整理，看到实际空位增加 |
| P1 | 主力角色优先获得可用装备，强化候选有投入顺序 | 依据当前库存和已配置的角色需求生成分配建议，指出冲突和缺口 |
| P2 | 攻略更新和分段强化减少人工操作 | 规则有版本依据；每次强化后重新识别，并遵守用户预算 |

P0 的“可清理”表示在本次配置和保留规则下没有保留理由，不承诺对未来所有角色与玩法都无用。若可靠判断出的数量不足以达到清理目标，应报告差额，不能为了腾空间自动降低标准。

## 2. 范围与关键判断

### 2.1 原始需求如何落地

| 需求 | 首版处理方式 | 后续扩展 |
| --- | --- | --- |
| 理解圣遗物加成 | 复用现有角色评分规则，并保留主词条、套装和有效副词条判断 | 加入队伍条件、充能门槛和完整配装计算 |
| 按持有角色查当前攻略 | 用户先选择已有角色、主力角色及玩法，使用核对过的本地规则 | 按角色联网更新攻略，记录逐篇版本与假设 |
| 筛选并废弃无用圣遗物 | 输出可清理清单，用户复查并执行；后续可自动选择待分解件 | 根据使用反馈增加自动化范围 |
| 主力优先 | 先为主力保留装备与候选，避免把潜在升级件放进清理清单 | 完整配装搜索、跨角色分配 |
| 强化策略 | 输出值得试强化的候选、下一检查点和停止条件 | 在预算内逐段强化并重新判断 |

### 2.2 评价原则

圣遗物价值取决于套装、部位、主词条、有效副词条、当前等级与剩余强化机会，也取决于角色、队伍和武器。评分用于比较候选，不能独立决定去留。

- 保留需求取相关角色和玩法的并集；一件物品对任一目标有用，就不能仅因其他角色用不上而清理。
- 主力指主力队伍成员，包括辅助、治疗和后台角色；不等同于只优先主输出。
- 保留有价值的套外散件、当前过渡装备和有潜力的未满级装备。
- 不以“双暴低”“防御主词条”或“未出现在推荐套装中”作为通用废弃条件。
- 五星通常在 +4、+8、+12、+16、+20 出现副词条变化；待激活词条若已显示，先读取其内容和状态。随机强化只能评估概率，不能保证结果。
- 对已满级物品，后续可单独评估重塑；普通强化与重塑使用不同策略和预算。

机制依据：[KQM 圣遗物指南](https://keqingmains.com/misc/artifacts/)及[套装资料](https://library.keqingmains.com/equipment/artifacts)。

## 4. 首版用户流程

1. **设置角色和整理目标。** 用户选择已有角色，将正在使用的队伍标为主力，并填写希望释放的空位数。其他角色可标为备用或暂不培养。角色名单不完整时显示覆盖范围，不给出覆盖全账号的清理结论。
2. **扫描背包。** 只读取信息，保持锁定、穿戴和等级不变。识别后展示总数、成功数、异常数和是否扫完整。
3. **生成报告。** 将物品归入“保留”“优先试强化”“可清理”“待复查”；提供每件理由及适用角色。
4. **先处理可清理件。** 按最容易确认的批次展示，达到目标空位即结束本轮。用户可以先保留或排除某一件，重新生成清单。
5. **再处理试强化件。** 按主力需要和预期收益排序；用户手动强化至下一检查点，再扫描更新结果。首版不要求一次处理所有候选。

报告至少显示：

| 分类 | 用户需要看到的内容 |
| --- | --- |
| 保留 | 适用角色、保留原因、是否正在穿戴或被手工保护 |
| 优先试强化 | 优先级、适用角色、目标部位、当前等级、下一检查点、继续或停止的条件 |
| 可清理 | 部位、套装、主副词条、等级、定位信息、被哪些候选替代以及清理理由 |
| 待复查 | 不确定字段、缺少的角色规则、识别异常或定位冲突 |

首版报告优先使用本地 HTML，加 JSON 保存结构化数据；页面只读展示，不通过本地网页直接操作游戏。筛选、排序和搜索按角色、套装、部位、等级及分类提供。普通用户不需要编辑 JavaScript。

## 5. 首版实现边界

### 5.1 一个 JS 项目承担组织工作

实施时创建一个独立 JS 项目原型，通过现有调度器或 Pulonia 手动运行。开发目录按仓库已有脚本管理方式确定；不预设新增 WPF 页面、数据库、后台服务或调度系统。

内部只划分五项职责：扫描与字段规范化、角色与规则读取、逐件评估与保留、报告生成、后续操作适配。扫描逻辑不决定去留，评分函数不操作游戏，操作逻辑只处理已经复核的清单。

首版优先使用现有基础设置表单。若角色选择和报告设置确实需要更丰富的交互，再接入已有 HTML 设置页；不将新设置界面的验收作为清理原型的阻塞项。

### 5.2 数据要求

| 数据 | 必须内容 |
| --- | --- |
| 用户设置 | 已有角色、主力与备用分组、玩法、手工保护项、期望空位；未提供的武器或命座等信息标为未知 |
| 规则 | 角色与玩法、适用套装和主词条、有效副词条、来源链接、适用版本、获取时间及评分数据版本 |
| 扫描记录 | 账号或用户确认的扫描范围、游戏版本、画面规格、开始和结束时间、物品数量、完成状态及异常 |
| 物品 | 名称、套装、部位、星级、等级、主副词条、待激活状态、锁定、穿戴者、局部截图或原始 OCR、扫描位置 |
| 决策 | 分类、适用角色、保留或清理理由、参考替代件、建议检查点、规则版本 |

扫描位置只用于本次扫描定位，不作为永久物品编号。属性相同的两件圣遗物仍是两件物品；不能按名称或属性哈希直接合并数量。发生强化、分解、筛选或排序变化后，旧坐标失效，处理前重新定位并读取属性。

星级、锁定、穿戴者等影响清理的字段无法确认时，物品进入待复查。星级不能仅通过套装名称推断。

### 5.3 去留规则

规则按以下顺序执行，前面的保护规则优先：

1. 用户保护、已锁定或正在穿戴的装备保留；不会为清理而自动解锁或卸下。
2. 识别异常、规则缺失、扫描不完整或身份不确定的物品进入待复查。受影响范围不生成可执行清理清单。
3. 为主力及备用角色保留当前可用装备和潜在升级件；缺少完整配装信息时采用保守保留。
4. 另行保护优质散件、稀缺主词条和必要的低星过渡装备。保留数量根据需要该类物品的角色数设置，不能一律只留一件。
5. 对剩余物品，结合角色规则、已有替代件和剩余强化潜力判断是否可清理。条件不充分时进入待复查，不能由单件低分直接推导废弃。

对于同一用途的冗余件，先比较同套装、同部位、同主词条的候选，再检查有效属性、等级与潜力。不同属性方向各有优势时不强行排唯一名次；“被替代”也必须检查替代件是否已经被其他角色占用。

首版采用可解释的保留规则和候选排序，报告中明确尚未完成精确配装搜索。不能把该结果称为全局最优。

### 5.4 强化建议

首版输出建议，强化由用户操作。初期按“主力缺口 → 主词条与套装适配 → 有效副词条与剩余机会 → 已有替代件”排序，不先建设复杂概率优化器。

每个候选至少说明下一步强化到哪里、希望看到什么结果，以及何时停止。满级装备不再进入普通强化队列；已显示的待激活词条与实际生效词条分开处理。

后续概率模型应估计超过当前可用装备的可能性和改善幅度，再考虑经验与摩拉成本。主力已达基本需求后，备用角色的明显提升可能优先于主力的微小提升。

## 6. 攻略与角色优先级

首版先覆盖用户选择的主力角色及实际玩法，逐个核对规则；尚无规则的角色标为未覆盖。不得把“未覆盖”当作“此角色不需要任何装备”。

社区评分权重与攻略结论分开保存。miao-plugin 权重可用于排序，攻略用于解释套装、主词条、充能及队伍假设。联网更新后先展示差异，不在正在执行的清理批次中替换规则。

[KQM 攻略入口](https://keqingmains.com/)在调查时有 7.1 版本更新，但各角色攻略进度不同。记录逐篇版本，不能只根据网站首页或页面抓取日期判断规则已经适配当前游戏。

后续精确配装可通过 GOOD 格式对接 [Genshin Optimizer](https://github.com/frzyc/genshin-optimizer)。这是可选扩展，不阻塞首版清仓。跨角色分配需另外处理：同时出场的角色不能共用同一件装备，是否允许不同队伍换装由用户设置。

## 7. 分阶段计划与验收

以下阶段均待实施，顺序以尽快完成一轮可靠清理为准。

### 阶段 A 现成脚本试用与适配选择

- 固定所选社区脚本版本，核对许可证、配置和当前宿主兼容性。
- 用现有实时评分或辅助脚本检查代表性物品，包括主力装备、稀缺主词条、散件、未满级和待激活词条。
- 试验 OCRArtifacts 的只读扫描，核对页间滚动、末页和不同星级，记录遗漏、重复与误识别。
- 得出明确结论：哪些模块直接使用，哪些小改，哪些暂不可用；若扫描原型不可靠，只替换扫描部分。

验收：形成有样例依据的复用清单和扫描缺陷清单。脚本能运行不等于扫描准确；后台任务必须拿到终止结果。

### 阶段 B 清仓报告

- 适配只读扫描，建立结构化记录、异常列表与完成状态。
- 接入一个评分模块及已核对的主力角色规则，实现保留逻辑、分类和本地报告。
- 显示计划可清理数量、清理后的预计空位，以及用户目标是否可达。
- 用户根据报告处理一批物品，再读取背包数量核对实际释放空间。

验收：总数与逐件记录对得上；重复和漏扫不会静默通过；每个可清理件可定位、有理由；保护件、异常件和未覆盖需求不会进入清理清单。首版以本阶段完成为准，不承诺固定清理数量。

### 阶段 C 主力保留与强化队列

- 加入备用角色和多玩法规则，生成按角色和部位组织的候选清单。
- 为主力装备及候选预留数量，显示抢占同一件物品的冲突。
- 输出分段强化建议，支持用户手动强化后的重新扫描和分类更新。

验收：同一件物品不会被重复承诺给同时出场的角色；可以解释某件为何先于另一件强化；强化后等级、属性和建议会更新。

### 阶段 D 减少重复操作

- 可选：依据已确认的规则配置游戏内锁定辅助，默认保留用户已有方案。
- 可选：按已复核清单在游戏中选择待分解物品；先确认已选数量与内容，再由用户确认不可逆处理。
- 加入攻略更新与可选的精确配装对接。
- 最后才实现预算内分段强化：材料来源受限，每次执行后读取实际等级、词条和消耗，支持中断。

验收：旧坐标和旧报告不能直接驱动操作；身份或数量不符时停止；停止后不自动重放消耗动作。普通强化和重塑分别设置执行范围与资源预算，不能共用一个“自动处理”开关。

## 8. 验证与交付边界

## 9. 首次试用所需配置

开始实施原型时，可先使用离线样例，不等待账号信息。进入真实背包试用前需要：

- 已有角色名单，至少标明当前主力队伍和近期准备培养的角色。
- 主力玩法；武器、命座等未知项可以后补，但会限制精确判断。
- 希望释放的空位，以及愿意为备用角色和未来用途保留多少装备。
- 游戏版本、语言和分辨率；首轮优先验证社区脚本已有的简体中文、1920×1080、16:9 路径。

默认采用保守清理，保留锁定、穿戴和手工保护件。自动强化预算默认未设置，不执行资源消耗。首轮根据实际报告调整保留标准，不在没有库存证据时预设统一毕业分数。
